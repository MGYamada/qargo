# Executable object identity

Explicit, sibling and PATH selection share one capture and launch implementation for qlippy, qlifmt and qlidoc. Open the selected ordinary executable once with no-follow/nonblocking flags, copy at most 256 MiB, and reject changes to its device/inode, permissions, size, modification time or status-change time during capture. Hash the captured bytes. Subsequent installation-path changes have no effect on the command being launched. Same-release, linked Qleisli/profile, closed response schemas and process-group cleanup remain required.

On Linux and Android, capture into an anonymous `memfd`, seal writes, growth, shrinkage and further seal changes, and launch through the live parent's `/proc/<pid>/fd/<descriptor>`. The parent retains that descriptor through response/artifact validation. Parent procfs paths also let shebang interpreters read captured script bytes after close-on-exec closes child descriptors. Procfs access and executable memfd support are required; unavailable or policy-disabled facilities fail explicitly. `MFD_EXEC` is requested on newer kernels, with an `EINVAL` fallback for kernels predating that flag. There is no mutable-path launch fallback.

On macOS, copy into an exclusively created private temporary directory, close the writer, and keep read-only file and directory descriptors. Set both the file and its private directory to owner read/execute only (`0500`). Launch the private copy and validate its named and held object identities, modes, sizes, modification times and status-change times before launch and after execution. Installation-path A/B/A replacements cannot redirect this launch. Private stage A/B/A tampering is rejected; cleanup restores write permission only to Qargo's own held directory. As with private source snapshots, Qargo owns and controls this temporary state within the operating system's user/process boundary.

Host identities on Linux and Android hash an opened `/proc/self/exe`, which identifies the running executable object even after its original pathname is renamed or unlinked. macOS uses the safe `libproc` API for `PROC_PIDREGIONPATHINFO` on an address in the linked executable, then checks the opened image file's device/inode against that kernel-provided vnode. It additionally rejects any vnode status change after process creation, including rename, chmod and in-place writes. Changed, deleted or inaccessible macOS images fail with `tool_identity` instead of reporting a replacement file's digest. The macOS implementation uses the 64-bit Darwin ABI supported by the standard x86_64 and ARM64 bundle, available before the macOS 11 deployment target. Other operating systems fail explicitly until an object identity implementation is provided.

Executable digests remain provenance metadata. Product version, Qleisli version, finite profile and matching source identities retain their separate meanings and do not certify arbitrary selected tools.
