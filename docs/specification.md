# Qargo and the standard Qleisli tools: specification

Status: public contract for the experimental 0.1.x releases; manifest schema version 2 and independent result schema version 1. Derived from [Qleisli issue 53](https://github.com/MGYamada/Qleisli/issues/53).

Supported release platforms are Linux and macOS, validated with Rust 1.85 and stable. Windows and Android are outside the 0.1.x support contract. Starting with 0.1.1, distribution includes the complete GitHub source archive or tagged checkout and the qargo crates.io package, which must install all four executables. No prebuilt executable assets are provided. A crates.io package must build independently from its packaged sources and registry dependencies. Repository development uses Cargo manifests/lockfile outside the qrate snapshot. The published qargo package compiles the canonical qrate engine sources as internal modules, with no dependency on the three private development packages. Packaging and installation are verified independently of Git source archives.

The documented CLI, independently versioned qargo.result, qlippy.result, qlifmt.result, and qlidoc.result formats (each version 1), and exit codes remain compatible within 0.1.x. Incompatible manifest/result changes require a new schema version, independently of product versions. Version 0.1.3 introduced manifest schema 2 to require an explicit Qleisli edition; schema-1 manifests must migrate and are rejected. Diagnostic prose and the internal Rust library API are not stable interfaces. Qargo, qlippy, qlifmt, and qlidoc must come from the same product release. The standard bundle consists of the three tool qrates, developed together at 0.1.4; Qargo still manages one qrate per operation.

## Boundaries

The [ecosystem policy](ecosystem-policy.md) adopts a curated stdlib center with future extensions bound to trusted sources, authenticated namespaces, and fixed identities. Public registry and automatic semver resolution are deferred. Qargo will not introduce arbitrary qrate build hooks, native procedural macros, dependency-install scripts, or global feature unification. These are design constraints on future Qargo operations, independent of Cargo's Rust implementation build machinery.

Qargo manages one local Qleisli qrate. Cargo builds, packages, and installs the Rust executables outside Qargo operations; no Qargo command invokes it. crates.io distribution does not add a Qargo registry or Cargo-backed qrate operations. Qargo has no Rust target, dependency solver, registry, downloads, publishing, Qargo.lock, or shell hooks. Zero .qli or .qlt files are supported. Each standard qrate includes src/smoke.qli, a minimal unitary identity operation used to exercise qrate management, and no .qlt files. Each complete Rust engine, CLI, and Rust test sources belong to its qrate and are captured as raw inputs. Shared snapshot, diagnostic, identity, and syntax support belongs to qlippy and is reused by qlifmt and qlidoc. Developer Cargo configuration lives outside the qrates in the repository root and rust/<tool>/Cargo.toml. Capturing .rs files does not authorize Qargo to compile or run them.

A qrate comprises Qargo.toml, a source root, a QLT test root, a documentation root, and deterministic local identity/build metadata. All three roots must exist as directories, may be empty, are UTF-8 qrate-relative paths, and must not escape the qrate, traverse symlinks, overlap each other, or include the reserved target directory. Unsupported schema versions and unknown fields are rejected.

The semantic subject of a qrate is its local Qleisli modules, public declarations, and contracts checked by the selected Qleisli implementation. Its raw input identity is a provenance envelope and can also contain host-language sources, tests, and documentation. Including Rust in that envelope does not extend Qleisli checking to Rust or make the host engine part of a proved Qleisli interface. The standard tool qrates are management examples whose smoke interfaces do not describe or certify their Rust engines. Schema 2 provides local source management, an explicit language edition, and provenance; it does not promise registry identity, dependency compatibility, or a complete semantic package contract.

In 0.1.4 the acceptance implementation is the linked Qleisli 0.2.1 ordinary checker. Qargo and qlippy record that linked version, finite-v0 profile, and actual host executable digest. A `qleisli` executable on PATH is not selected or consulted. The embedded standard library belongs to that linked checker distribution, not to an independently resolved qrate; local source identity excludes it and must be interpreted together with the recorded tool identity. This metadata identifies a processing implementation, not a proof. See [toolchain evolution](toolchains.md) for the future separation of qrate-selected acceptance toolchains and orchestration.

```toml
schema-version = 2
[qrate]
name = "qlippy"
version = "0.1.4"
edition = "2026"
[source]
root = "src"
[tests]
root = "tests"
[docs]
root = "docs"
```

Names use ASCII letters/digits, hyphens and underscores, beginning with a letter. Versions are nonnegative canonical decimal MAJOR.MINOR.PATCH. Every valid manifest must explicitly include `edition = "2026"` under `[qrate]`. The edition is a TOML string, and `"2026"` is the only supported Qleisli edition. Omission has no default and is an `invalid_manifest` error; numeric/date/boolean/array values are also invalid. Other strings produce `unsupported_edition`. Qrate operations validate the edition before processing sources or invoking tools, including for empty roots. The captured raw manifest binds the edition to the input identity and build snapshot. The Rust implementation uses its own explicit Cargo edition `"2024"`.

To migrate a schema-1 manifest, set `schema-version = 2` and add `edition = "2026"` under `[qrate]`. Unsupported schema versions produce `unsupported_manifest_version` with this migration suggestion; result-envelope versions remain 1. All valid manifest examples and fixtures must include the edition, and future editions must receive explicit support before they can be accepted.

Explicit --manifest-path takes precedence; otherwise search current and ancestor directories for Qargo.toml. A malformed found manifest is an error, never grounds for continuing upward.

Dependency tables, including [dependencies] and [dev-dependencies], are unsupported and rejected with an invalid_manifest diagnostic and a suggestion to use local Qleisli modules and external developer Cargo configuration. Unsupported Cargo-style dependency commands such as qargo add remain usage errors with suggestions for supported local operations.

## Commands

- qargo check [--manifest-path=PATH]: validate and freeze inputs, then check the .qli source root using Qleisli 0.2.1's ordinary public check API. Library roots do not require main. All local definitions receive normal source/IR checks.
- qargo build [--manifest-path=PATH]: check, then emit the exact declared input snapshot, a public local module/declaration index, and a build record under target/qargo/<input-id>/<tool-id>/ (SHA-256 hex components). It does not compile the Rust engine or claim to produce executable quantum code.
- qargo lint [source-root] [--manifest-path=PATH] [--qlippy=PATH] [--deny-warnings]: with an explicit source-root, lint that standalone root; otherwise resolve the qrate's source root. A source-root and --manifest-path are mutually exclusive and their combination is a usage error. Invoke the qlippy executable on a frozen source snapshot. Explicit tool paths are authoritative; otherwise use an executable sibling of qargo, then PATH. Never automatically build, install, download, or silently fall back after a selected tool fails.
- qargo fmt [source-root] [--manifest-path=PATH] [--qlifmt=PATH] [--check]: format a standalone source root when explicitly provided; otherwise format the qrate source root. A source-root and --manifest-path are mutually exclusive and their combination is a usage error. Invoke qlifmt on a frozen copy, validate the candidates, and apply them to the original sources only after confirming that captured source contents are unchanged. --check reports differences without updating the originals.
- qargo doc [--manifest-path=PATH] [--qlidoc=PATH] [--document-private-items]: generate Markdown for the qrate source root through qlidoc on frozen sources; validate the child response and all generated files before publishing under target/qlidoc/<input-id>/<tool-id>/<public-or-all>/. The path components use SHA-256 hex without the sha256: label.
- qargo test [--manifest-path=PATH]: validate the qrate, then fail explicitly with backend_unavailable because QLT execution is not implemented, including empty packages. Do not substitute a host-language test runner.
- qlippy <source-root> [--deny-warnings]: freeze .qli sources, check their actual source/IR through Qleisli 0.2.1, then lint local ASTs. Compiler failures prevent lint evaluation.
- qlippy --list-rules: enumerate rule groups and promotion policies without reading sources or calling Qleisli. Accept --format=json for the rule catalog described below; do not combine with source arguments, --deny-warnings, --help, or --version.
- qlifmt <file-or-source-root> [--check]: parse captured .qli sources, generate validated formatting candidates, and write them unless --check is requested.
- qlidoc <file-or-source-root> [--output=PATH] [--document-private-items]: parse documented modules and publish Markdown. The default output is target/qlidoc/<source-id>/<tool-id>/<public-or-all>/ under the current working directory; --output selects a complete output directory.
- --version on each executable: report engine version, actual executable SHA-256, linked Qleisli version, and finite-v0 profile.

All commands accept --format=json once, anywhere. All four executables support --help and --version. Unknown/repeated options, invalid option combinations and missing arguments are usage errors. Path options accept both equality syntax (--manifest-path=PATH, --qlippy=PATH, --qlifmt=PATH, --qlidoc=PATH, --output=PATH) and space-separated syntax (--manifest-path PATH, etc.). Empty values and repetition across either form are rejected. A space-separated value cannot start with a hyphen; use equality syntax or a ./ prefix for such paths. --format=json retains equality syntax. Handled JSON-mode results emit exactly one UTF-8 object followed by LF on stdout, with no progress/log prose. Human diagnostics use stderr. Exit codes: 0 success (including warnings), 1 execution/validation/compiler/backend failure, denied warnings, or formatting differences in --check mode, 2 usage. --deny-warnings applies only to linting; --check applies only to formatting; --document-private-items applies only to documentation.

For zero .qli files, check/build/lint/fmt/doc succeed with source_count=0 and a Qleisli step of status=not_run, reason=no_sources. They do not call the Qleisli checker and do not report verified=true. Bundled std modules are not local package declarations. No test or documentation status is inferred from a source check. Nonempty formatting and documentation inputs use syntax parsing only; qleisli_check is not_run with reason=syntax_only, without calling ordinary type, ownership, or contract checking.

## Result version 1

Each envelope has exactly format (qargo.result, qlippy.result, qlifmt.result, or qlidoc.result), version (1), command, outcome (ok/error), diagnostics (array), and result (object or null). Diagnostics have exactly id, category (qargo/compiler/lint/tool/usage), severity (error/warning), primary (location or null), message, and suggestion (string or null). Locations have path, start, end, line, column. Spans are half-open original UTF-8 byte offsets, and line/column are one-based Unicode scalar coordinates; CRLF counts as one newline. Local paths use relative forward slashes. Bundled locations use std:// labels. No lossy encoding or absolute temporary paths are permitted.

Success has no error diagnostics. Failure has at least one error diagnostic except denied-warning failure, which retains the warning diagnostics. Formatting differences in --check mode produce formatting_required with severity error. Explanatory message and suggestion text are not stable identifiers. Lint results include source_count, source_id, a qleisli_check step, and tool information (engine/version, linked Qleisli version, profile). Compiler rejection retains that input/tool binding with qleisli_check.status=failed; input capture or usage failure may have a null result. Steps have status passed/not_run/unavailable/failed and a reason. For qlippy's `qleisli_check`, nonempty inputs allow exactly `passed` with `reason=null` or `failed` with `reason="compiler_error"`; empty inputs allow exactly `not_run` with `reason="no_sources"`. Other failure reasons, including null, are rejected by Qargo transport validation. A denied-warning result still includes the actual analysis result. Qargo lint also records its orchestrator identity and execution steps, and includes input_id when a qrate was captured. Build-output failures retain the captured input and source-check outcome.

Qargo treats child-tool output as untrusted transport: validate the closed envelope and diagnostic/location shapes, format/version/command/outcome, command-specific diagnostic categories, tool/profile compatibility, exact same-release product version, actual selected executable digest, source_count/source_id binding, and exit/outcome consistency. Reject invalid JSON, unknown formats, malformed locations, truncated responses and process failures. Remap locations only against the captured source bytes. Selected tools run in a dedicated process group on supported Unix platforms, with a 30-second execution deadline, a 4 MiB stdout budget, and a 64 KiB stderr budget. Unexpected stderr, oversized output, I/O failures, and deadline expiry abort transport and terminate the process group, including descendants that inherited it. Cancellable nonblocking pipe readers keep inherited descriptors from extending capture or cleanup beyond the deadline. Unsupported process-group platforms fail explicitly. Child stderr is handled as tool output, never mixed into JSON stdout. Tool selection for all three children uses explicit path, executable sibling of Qargo, then PATH, with no fallback after a selected tool fails.

Formatting results contain source_count, original source_id, qleisli_check, tool, formatted_source_id, changed_files, updated_files, check, and diff. Paths are sorted source-relative labels. changed_files identifies differences; updated_files identifies files actually written, and is empty for --check. All candidate bytes must pass syntax, token/comment preservation, and doc-comment attachment validation. Qargo adds orchestrator and input_id when a qrate was captured; it revalidates candidates on the private copy and source identity before applying changes. An application I/O failure retains updated_files so partial progress is explicit.

Documentation results contain source_count, source_id, qleisli_check, tool, document_private_items, artifact_path, and a sorted files array of {path, sha256}. Qargo adds orchestrator and input_id and validates the exact file set, path safety, SHA-256 digests, and rendered content against frozen sources. The artifact_path is relative for default outputs; explicit standalone output may be an absolute path. Neither result contains verified=true.

## Lint rules

All three rules default to warning; --deny-warnings makes warnings fail without rewriting source. Suggestions are prose only.

- unused_import: flag an import only when there is no possible use in declaration bodies, meaning references, static parameters/arguments or capability requirements. Conservative name matching intentionally retains imports under ambiguous shadowing.
- redundant_repeat_one: repeat_static(1, f, input) and repeat_op(1, op). Point to the complete redundant constructor.
- double_inverse: inverse_op(inverse_op(op)). Point to the complete outer constructor.

Do not cancel arbitrary gates, use floating-point equivalence, infer clean release, or claim algorithm correctness. Syntax and all normal compiler checks apply before these advisory rules.

Rule policy is exposed by qlippy --list-rules --format=json in a qlippy.result version-1 envelope with command=list-rules. Its result has exactly catalog_version (1), groups, promotion_policies, rules, and tool. Group and promotion-policy entries have exactly id and description. Each rule has exactly id, group, promotion, default_severity, description, and rationale. Rules are sorted by diagnostic ID. Catalog versioning is independent of product and result-envelope versions; incompatible catalog changes require a new catalog version. It contains no source binding, qleisli_check, or verification claim. Existing lint diagnostic/result shapes are unchanged; diagnostic IDs join to catalog IDs.

The idiom group covers local conventions, import hygiene, and stdlib idioms; complexity covers unnecessary syntax; resource reserves a place for advisory resource-use observations and currently has no rules. A group never establishes Resource Safety. Promotion values are advisory (remains advisory, with no planned acceptance/theorem obligation), checker_candidate (may be retired when ordinary checking enforces the condition), and theorem_candidate (may be retired when a Qleisli theorem obligation covers it). Candidate status is a maintenance policy, not evidence or an acceptance condition. A future promotion must identify the covering checker diagnostic or theorem and its toolchain version in the catalog/release migration documentation before retiring a rule. This catalog has no such promotions yet.

| Rule | Group | Promotion | Reason |
| --- | --- | --- | --- |
| unused_import | idiom | advisory | Unused imports remain valid; removal is import hygiene. |
| redundant_repeat_one | complexity | advisory | A shorter spelling is optional; count-one repeat remains valid. |
| double_inverse | complexity | advisory | A shorter spelling is optional; nested inverses remain valid. |

Possible future proofs of repetition or inverse identities do not make these style preferences theorem obligations. All three default severities remain warning. Groups do not currently provide CLI selection or severity configuration.

## Formatting and documentation

qlifmt uses four-space indentation and a target line width of 100; indivisible syntax tokens or comments may exceed the target. It preserves syntax-token values, comments' exact content and order, doc-comment attachment, and LF/CRLF convention. All files are parsed and all candidates validated before the first write. No import reordering or configuration file is provided in 0.1.4. Type and ownership errors do not prevent formatting when syntax is valid. --check prints a human-readable diff (or places it in the JSON diff field), returns 1 on differences, and writes no source files.

qlidoc calls Qleisli 0.2.1's parse_documented_module and renders module docs, declaration signatures, and attached doc comments to Markdown. The default visibility policy includes only public declarations, following rustdoc's public/private selection convention; --document-private-items includes nonpublic declarations. It writes index.md plus modules/<relative-source-path-without-.qli>.md, including nested source paths. Handwritten qrate documentation remains an ordinary captured input rather than being rewritten. Documentation examples are not executed, and type-invalid but syntactically valid modules can be documented. Empty inputs produce an index without a Qleisli verification result.

Complete documentation directories are staged and published atomically without replacing existing output. Exact repeated contents are validated and reused; conflicting contents, symlinks, and unsafe paths fail. Generated files cannot feed back into captured qrate inputs. Future HTML generation may adopt qlidoc-specific CSS, colors, and layout; visual compatibility with rustdoc is not required. HTML and styling are outside the 0.1.4 implementation.

## Snapshots, identity and artifacts

Capture original bytes once, using sorted UTF-8 relative paths; reject symlinks and nonregular input files. Enforce bounded input collection (1 MiB/file, 16 MiB total, at most 4096 files and directory depth 64). Qleisli's own default source budget also remains in force. Identity uses SHA-256 with domain separation and length framing of paths/bytes. Qrate identity covers raw manifest bytes and all files in the three declared roots. Standalone source identity covers .qli files relative to their source root, independent of qrate location. Hidden directory markers are ordinary qrate inputs, never .qli sources.

Checks, linting and artifacts must consume the captured bytes, not a later read of the user's files. Source IDs exclude absolute paths, timestamps, generated files and tool versions; records bind tool identities and profiles separately. Record the actual host executable digest, embedded Qleisli version, selected steps and outcomes. Metadata and success are not proof. QLT execution remains unavailable. Formatting and documentation success establishes only the documented syntax-based processing, never mathematical evidence.

Build artifact directories contain snapshot/Qargo.toml and declared inputs (including .rs files), all three declared root directories even when empty, module-index.json (public declarations in local modules, sorted), and build-record.json. The record explicitly marks QLT as not_run with reason=backend_unavailable and qlidoc as not_run with reason=not_requested; qargo build does not generate documentation. Output uses relative paths, contains no timestamps, and is installed atomically without replacement from a complete sibling staging directory. Build and documentation use the same descriptor-anchored publication kernel in qlippy: ancestor traversal, staging creation/population/cleanup, existing-artifact validation, and no-replace installation use held directory descriptors and reject symlink redirection. Revalidate directory device/inode identities before installation and reuse. Explicit empty directories remain part of the exact artifact inventory. Atomic publication is supported on Linux, Android and Apple platforms; other platforms fail explicitly until a safe implementation is added. A repeated identical build validates and reuses identical artifacts; inconsistent or symlink outputs fail rather than overwriting unrelated data. Distinct host executables keep separate records for the same input ID, allowing engine rebuilds without erasing older provenance. Generated output cannot feed back into inputs. Different toolchains/operating systems have no promised Rust-binary byte equivalence.

## Development and validation

Rust-only development commands (Cargo build/test/doc/Clippy) build and check the engines; they are outside Qargo operations. Required integration checks include zero-source qrate behavior; existing lint rules and nonmatches; compiler rejection and shadowing/static references; UTF-8/CRLF and multiple modules; relocation/content-change identities and frozen inputs; unavailable QLT; tool absence/failure, incompatible versions, invalid JSON, source binding, and unsafe outputs; and Cargo/Rustdoc PATH traps. Formatting tests cover idempotence, non-writing --check, syntax preservation, long lines, ordinary/doc/nested comments, input races, and partial application failures. Documentation tests cover module/declaration docs and signatures, private filtering, Markdown fences, empty input, parse failures, syntactically valid type-invalid input, deterministic reuse, and output conflicts/symlinks. Engine inputs are generated from Rust strings in temporary directories; each tracked smoke sample also exercises mixed .rs/.qli qrate snapshots and public module indexing. Linux/macOS × Rust 1.85/stable CI validates all targets, the complete Git source archive, the standalone .crate inventory, and installation of all four executables from that package. Private development packages remain unpublished.
